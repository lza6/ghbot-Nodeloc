## 1. 项目全貌与现状盘点（基准线）

### 1.1 技术栈

| 维度 | 现状 |

### 1.4 当前基线验证结果（2026-08-22 实测）

```text
npm run typecheck → 通过（0 错误）

npm test → 68 个测试 / 66 通过 / 2 失败
```

**⚠️ 2 个失败的测试**（编码时排第一优先级修复，详见 [第 3 节](#3-p0-基线先补齐测试与修复已知问题)）：

1. `test/repository-knowledge.test.ts:19` — 期望 `# Architecture\n\nUse npm test.\n` 往返导入后
   仍是 511 字符，实际得到 438 字符。**疑似跨平台 CRLF 行尾差异**（Windows 上 `normalizeKnowledge`
   `.trim()` 后追加 `\n`，往返读写时行尾被 git/编辑器转为 CRLF 或相反）。
2. `test/chat-mention.test.ts:109` — 同样报 `438 !== 511`，是同一行尾问题的连锁表现。

> 注：438 与 511 之差恰为 73 字符 = 源字符串被行尾转换后字节数变化所致，与 CRLF/LF 在 `Buffer.byteLength` 与 `fs.stat` 上的差异一致。修复方向是在测试或实现层做行尾归一，详见 3.2。

### 1.5 已识别的结构性问题（审计结论，详细见第 10 节）

1. **无 linter/formatter**：只有 tsc + test，无 `eslint`/`prettier` 把关，代码风格漂移风险。
2. **测试覆盖不足**：核心编排 `review/processor.ts`（>1600 行）无直测；`webhook/server.ts` 队列逻辑、
   `storage/cacheStore.ts` 上传路径、`github/checks.ts` 忽略规则、`ai/apiProxy.ts` 均仅有间接覆盖。
3. **withRetry 无条件退避**：对 4xx（非 422 review 回退场景）与 5xx 一视同仁，浪费配额、放大延迟。
4. **R2 上传无失败隔离**：`cacheStore.ts` 中保存失败会把整个 Actions run 标记失败（只在 finally 里
   warn，但 `savePersistentCache` 抛错会导致主流程 `eventFailed`？—— 实际是 finally 中 catch 了，见 10.3）。
5. **事件处理全部串行**：`runReview.ts` 的 `issue_comment` 分支依次跑 recheck→conflict→chat，
   任一失败会中断后续处理。
6. **安全防线存在单点**：`isBotLogin`/`isBotSender` 只按 login 字符串匹配（大小写忽略），
   未校验 commenter 的 `type==="Bot"`；快照排除清单为硬编码数组，未集中在单处配置。
7. **webhook 仅支持 `chat/completions` 单端点代理**，不支持流式 SSE 透传（`apiProxy.ts` 中
   `upstream.body` 已用 `Readable.fromWeb().pipe` 支持流式返回，但 goose 侧请求非流式）。
8. **错误消息偶现泄漏路径/命令细节**：`commandFailureOutput` 返回原始 stderr，虽经
   `describeConflictResolutionFailure` 归类，但兜底分支直接暴露编排细节。
9. **无指标/心跳**：webhook 只有 `GET /healthz`，无运行期指标（审查时长、goose 调用次数、失败率）。
10. **依赖无版本锁定策略**：`^8.2.0`、`^21.0.2` 等 carat 依赖在 CI 中会浮动刷新；
   无 `package-lock.json` 校验策略（实际上锁文件在仓库里，但 CI 用 `npm ci`，需确认 lock 与
   package.json 同步）。

## 3. P0 基线：先补齐测试与修复已知问题

### 3.1 修复 2 个失败测试（第一优先，编码前其他事都不要做）

**目标文件**：
- `test/repository-knowledge.test.ts`
- `test/chat-mention.test.ts`
- (可能) `src/repository/knowledge.ts` 的 `normalizeKnowledge`

**根因**：`normalizeKnowledge` 做 `content.trim() + "\n"`。Windows 上写入测试临时目录时
`fs.writeFile` 原样写入 LF，但读取返回 `\n`；导致往返后内容长度不一致的根因更可能是
**写入的源字符串本身不含预期换行，或 `.trim()` 与期望字符串的换行数不匹配**。

**修复方案（推荐，先证后改）**：
1. 先写一条最小复现测试：`writeKnowledgeScratch(root, X); assert.equal(await readKnowledgeScratch(root), X)`，
   对 X 分别取 `"# A\n\nB\n"` 与 `"# A\r\nB\r\n"`，打印实际往返结果的 `JSON.stringify`。
2. 定位差异点后**在实现层统一 LF 行尾**：`normalizeKnowledge` 改为
   `content.replace(/\r\n/g, "\n").replace(/\r/g, "\n").trim() + "\n"`（保证任何平台往返稳定），
   测试断言保持 LF。
3. 若实现改动会影响 R2 对象字节数，`saveRepositoryKnowledgeCache` 与
   `validateRepositoryKnowledge` 的字节上限校验在归一化后进行（先 normalize 再算字节数）。

**验收**：`npm test` 68 项全绿；`npm run typecheck` 通过。

## 4. P1 可靠性：审查链路健壮性

### 4.1 withRetry 区分错误类型（可重试性）

- **现状**：`src/retry.ts` 对所有错误无差别重试，且 baseDelay 固定 1000ms×次数。
- **改进**：支持选项 `retryable: (error) => boolean`，默认对网络/5xx/限流（`status>=500`、
  `ECONNRESET`、`ETIMEDOUT`、`EAI_AGAIN`、`429`）重试；对 4xx（除 409 冲突、429 限流外）不重试。
- **验收**：新增测试覆盖「4xx 不重试」「5xx 重试后成功」「429 到达上限抛错」。

### 4.2 issue_comment 事件三链路隔离

- **现状**：`runReview.ts` 中 `/recheck`、`/conflict`、`@bot` 依次等待，前一个抛错中断后两个。
- **改进**：三者在 `Promise.allSettled` 语义下并行或顺序容错执行——各自 try/catch 打 warn，
  不互相中断；`/recheck` 与 `/conflict` 互斥（同时出现时仅执行 `/recheck`，打 warn 提示冲突命令被跳过）。
- **验收**：新增集成测试（mock octokit），构造 `commentBody="/recheck\n/conflict"` 断言只触发 recheck；
  构造 recheck 抛错时 conflict 仍执行。

### 4.3 审查结果校验前置（fail-fast）

- **现状**：`gooseReviewer.ts` 的 zod schema 在解析时才暴露问题，且无「line 是否在新增行内」的校验。
- **改进**：审查结果解析后立即调用 `normalizeReviewDecision(decision, files)`：
  - 过滤掉 `path` 不在文件列表中的 finding（转成 unposted 提示）；
  - `line` 非正整数 → 归入 unposted；
  - 校验 `result.canMerge=false` 与 `change.length>0` 的一致性（不一致以保守为准：有 change 则拒绝合并）。
  - 输出增加 `warnings: string[]` 供日志与评论展示模型输出不规范数量。
- **验收**：新增测试构造脏 decision（伪造 path/负数 line/矛盾 canMerge），断言净化结果与 warnings。

### 4.4 审查运行期间的“陈旧检测”补强

- **现状**：`processPullRequest` 中仅在 model 返回后二次 GET PR 校验 head，若 PR 在审查中多次变化
  会浪费一次完整审查。
- **改进**：在调用 `reviewer.review` 前先快照 head；返回后校验；若 head 变了且小 patch 总量
  ≤ `maxPatchChars/2`，可在**同一 prompt** 追加“新变更段落后缀”让其合并审（降低成本），
  否则丢弃重新审。实现时保持「不直接复用旧决策」红线。
- **验收**：测试覆盖「head 未变 → 正常评论」「head 变 → 追加段落后缀路径」。

### 4.5 调度复核（schedule）防重复合并竞态

- **现状**：`processScheduledPendingMerges` 与 `processPullRequestReviewApproval` 都可能触发合并；
  Actions 并发 run 下可能出现“同一 head 的重复合并请求”。
- **改进**：合并前校验 `pull.merged` 状态与 `merge_commit_sha`；用 `octokit.rest.pulls.get` 检查
  当前 `state==="open"` 后置校验再 merge；merge 调用本身由 GitHub 保证幂等（第二个返回 405/409 时
  视为已合并，打 info 而非 error）。
- **验收**：测试覆盖「合并后 pull 已 merged → 不重复请求」。

### 4.6 webhook 队列任务失败幂等

- **现状**：`WebhookTaskQueue.drain` 中失败会从 `seen` 删除 deliveryId 允许 GitHub 重试，但
  任务本身没有任何 on-disk 持久化，进程重启即丢队列。
- **改进**（低成本版）：失败重试上限（每 task 至多 2 次，仍从 seen 删除）；得更完善的做法见 P4.4。
- **验收**：测试覆盖「task 重试 2 次后放弃并允许 GitHub 重投」「成功任务保持去重」。
